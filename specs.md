## 1. Project name and overview

### Project name

FactVerify Civic Agent

### Overview

A full-stack autonomous web agent and media validation platform (React frontend + Python FastAPI backend backed by Playwright) that automates public service navigation while auditing truth data in real time. The engine ingests unverified public service claims, viral media files, and citizen profiles, matches them against trusted database registries and knowledge graphs using multi-modal forensic models to detect synthetic manipulation, and executes automated web workflows on legacy government portals to safely retrieve verified official documentation for the citizen.

## 2. Problem statement

### Problem

* Current pain: Citizens lose countless hours trying to access essential public services, scholarships, or entitlements due to a fragmented digital landscape where confusing, non-API legacy government portals sit right alongside a flood of viral misinformation, misleading claims, and hyper-realistic deepfake announcements regarding policy rules and eligibility criteria. When individuals search for how to secure public aid, they are forced to navigate an overwhelming mix of online text strings, deceptive media, and broken UI forms without knowing what information is true or how to process the application safely.
* Concrete impact: Misleading altered policy statements spread unchecked, causing citizens to fall victim to fraudulent schemes or miss genuine application deadlines, while the sheer friction of manually navigating legacy platforms results in errors that cost vulnerable households thousands of dollars in lost aid.
* Desired outcome: A single, secure AI verification and execution framework where a user can input any public service claim or media clip alongside their profile; the engine immediately maps out the authentic truth data, isolates manipulated regions or fake guidelines, and instantly spins up a background browser agent to execute the verified application route, returning a definitive tracking receipt to the citizen.
* Non-goals: The application does not automatically submit financial transactions or digital compliance approvals without a human-in-the-loop validation gate, and it does not store user passwords long-term.

### Users and tasks

	• Tasks: Upload public service announcements, text links, or video clips to verify rules; provide a personal data background profile; monitor real-time browser agent logs; resolve manual-approval blockages; download finalized government receipts.
* Fact Checker & Public Auditor – professional power-user validating community distribution arrays.
	• Tasks: Ingest suspect public policy media streams, analyze regional heatmap forensic data overlays, configure automated verification playbook mappings, and export unified provenance markdown reports.

## 4. Core features

### Core features

* F1 – Multi-Modal Ingestion & Profile Mapping: POST /api/audit/ingest - accepts text blocks, social media post URLs, or media file blobs (.mp4/.png) along with user profile metadata, mapping everything into local structured data arrays.
* F2 – Verification & Media Forensic Analysis: POST /api/audit/forensics - deploys parallel vision models and text tokenization layers to cross-reference claims against trusted knowledge graphs, flagging metadata tampering or deepfake frequencies with a regional heatmap overlay.
* F3 – Autonomous Execution Browser Agent: POST /api/tasks/run - launches a background Playwright worker that takes the verified data parameters and logs into legacy portals to execute a bounded application path (max 10 steps).
* F4 – Human-in-the-Loop Approval Gate: GET /api/tasks/:id/state - yields live runtime trace logs and portal screenshots, shifting status to awaiting_approval if a CAPTCHA, payment portal, or verification discrepancy arises.
* F5 – Final Tracking & Receipts: POST /api/tasks/:id/complete - extracts the final text confirmation code or downloadable application PDF from the legacy site, storing it as an immutable audit record for the user.

## 5. Inputs and data sources

### Inputs and data sources

User inputs:
* Claim text (a forwarded message, announcement or transcript).
* A social media or web URL; the backend fetches the page text and checks the source domain.
* Media files: .png / .jpg images and .mp4 video (max 50 MB). Video frames are extracted with ffmpeg; audio transcription runs when an optional speech-to-text engine is installed, otherwise the user pastes the transcript.
* Citizen profile: full name, date of birth, phone, email, state, annual family income, course / institution, and the last 4 digits of the national ID. Stored encrypted.

Trusted data sources:
* Scheme registry (`backend/data/registry.json`): each official scheme with its official domains, benefit amount, application fee, income limit, deadline, eligibility and the portal playbook that applies to it. Teams replace or extend this file with data from official government sources.
* Trusted domain list (`backend/data/trusted_domains.json`): official domains (e.g. `*.gov.in`, `*.nic.in`) used to score URL sources.
* Scam pattern library (`backend/data/scam_patterns.json`): known fraud signals such as upfront fees, OTP requests, personal-number payments and false urgency.
* Optional AI reasoning: when `ANTHROPIC_API_KEY` is set, Claude adds a written analysis of the claim against the matched registry entry. The rule-based engine works without it.

Portal targets:
* Portal playbooks (`backend/app/agent/playbooks/*.json`): one file per portal, describing at most 10 steps and which profile field fills which form field.
* A sandbox scholarship portal ships with the app at `/portal` so the full agent journey can be demonstrated and tested without touching live government systems.

## 6. Processing rules and business logic

### Processing logic

* Multi-Threaded Validation Preceding Execution: When a user uploads a claim video, the system splits audio to text transcription for database claim-matching while running image frames through alteration detectors to calculate an aggregate confidence score (0.0 for Fraudulent to 1.0 for Authentic).
* Threshold-Gated Browser Launch: The autonomous browser automation agent will only spin up if the parsed instruction sources or links score above a 0.75 authenticity threshold, blocking deceptive loops from stealing user data.
* Bounded Operational Automation: The Playwright worker cannot exceed 10 discrete steps per application flow to prevent infinite recursive patterns or unexpected heavy traffic on public portal frontends.
* Safety & Review Intercepts: Any step hitting localized payment walls, ambiguous verification rules, or conflicting information checks forces the worker to capture browser state, pause execution, and alert the client via the approval gate UI.

## 7. Expected outputs and user experience

### Expected outputs and UX

* Screens & UI Components: A centralized dashboard featuring an interactive media player with color-coded warning overlays (red frames highlighting detected deepfake anomalies), side-by-side claim matching text feeds, an overall trust-gauge component, and a live terminal window mirroring the active automated browser progress.
* Summaries & Reports: A clean, downloadable audit document summarizing model certainty metrics, matched public policy registry references, and an immutable tracking receipt block displaying the finalized government system confirmation code.

## 8. Error handling and edge cases

### Error handling and edge cases

* Low-Resolution Integrity Loss: If an uploaded instruction file drops below 240p resolution, the system appends a structural warning (low_resolution_confidence_degraded = true) to the dashboard, warning that granular editing artifacts are less reliable.
* Missing Target Mapping Fields: If the verified government portal form requests a specific identity field that wasn't provided in the citizen's initial profile, pause automation instantly, adjust task status to missing_data, and highlight the required form box for the user.
* Portal Gateway Retries: If a legacy network portal times out mid-execution, the agent saves a local checkpoint and attempts a single retry; a secondary failure forces a task state of failed_at_step_X and preserves the run-trace for review.

## 9. Safety, privacy, constraints, and integrations

### Safety, privacy, constraints, integrations

* Data Lifespan & Encryption: All highly sensitive personal identity data is encrypted at rest with AES-256-GCM (SQLite for local runs; the storage layer can be moved to PostgreSQL for production) and wiped completely 24 hours after task completion. Only the last 4 digits of a national ID are collected.
* Portal scope: the agent only runs against portals that have a playbook. Live government portals must only be added where their terms permit automated assistance; CAPTCHAs are always solved by the human, never bypassed.
* Exploitation Safeguards: Proprietary forensic model signatures, validation criteria loops, and background browser playbook workflows are hidden behind system-level authentication tokens to prevent bad actors from reverse-engineering the engine's checking capabilities.
